Part 1 Quick Start — up and running in a few minutes

The core loop you'll use almost every time: find a device, look at what's plugged into it, add something new, wire it up. This part covers the handful of actions that make up most day-to-day use.

Signing in

Open LinkLedger in a browser and you'll land on the sign-in screen. Enter the admin username and the default password documented in the README (this is the only place that default lives — LinkLedger no longer takes passwords from environment variables).

The very first time you sign in as admin with the default password still in place, a reminder appears. It'll keep appearing on every login until you actually change the password from Settings — this page is exactly what it points you to.

Do this first on a real installation Sign in, go to Settings, and change the admin password before this instance is reachable by anyone else. See "Settings, accounts & backups" below for exactly where.

Browsing & search

Dismiss the reminder (or change the password first, your call) and you land on Browse devices — every device you've documented, as a grid of cards.

The search bar at the top matches as you type — name, role, or model. This is usually faster than scrolling the grid once you know roughly what you're looking for.

Reading a device page

Click a device — from search or the grid — and you're on its page: every port it has, and exactly what each one connects to.

Each connected row reads left to right: the port, its speed and any VLAN tag, then an arrow to whatever it's plugged into. If that chain passes through a patch panel, you'll see every hop, not just the final destination.

Adding a device

+ Add device, top right of any page. Give it a name, pick a role from the dropdown (this drives what options show up later — VLANs, PoE, and so on), and optionally a model and site.

Site and Role lists start empty/minimal The Site dropdown only offers whatever you've added under Settings → Sites. Role options can be trimmed from the full fixed list under Settings → Device roles, so you're not scrolling past roles you'll never use. Both are covered in "Settings, accounts & backups" below.

Adding ports

From a device's page, + Add port(s). A single name (eth0) creates one port; a range like Port[1-8] creates eight at once — handy for a switch. You can set a speed that applies to the whole batch.

Cabling two ports

Click the link icon on any unconnected port, or use + New cable at the top of any page to pick both ends from scratch without opening either device first. Search for the device, pick the port, done.

Physically moving a cable? A port that's already connected still shows up in these pickers instead of being grayed out — pick it as the new target and confirm the warning, and LinkLedger disconnects the old cable and makes the new one in a single step. See "Moving a cable in one step" in Part 2 below.

Editing things

A pencil icon edits a device or port in place — rename, change role/model/site, or (for ports) set speed, VLAN(s), or PoE. An ✕ disconnects a cable; a trash icon deletes a port or device outright (both ask for confirmation, since deleting a device takes its ports and cables with it).

To reassign a connected port to a new target in one step, use + New cable and pick that port as either end (see the callout above). To just disconnect a port without immediately reconnecting it elsewhere, use the ✕ icon — the link icon reappears in its place whenever you're ready to connect it to something new.

What's next

That covers the loop you'll use constantly: find, look, add, wire up, edit. Everything else — patch panels, wireless/virtual links, LAGs, PoE tracking, the path finder, reports, printing, and the settings/backup pages — is in Part 2 below, in the same order as the example network's own more unusual corners, so you can either read straight through or jump to whatever you actually need from the table of contents at the top.

Part 2 Complete Guide — every feature, and the edge cases

Everything Quick Start didn't cover: features you'll reach for less often, but that matter once your network gets more interesting than a flat switch and a few clients.

Moving a cable in one step

Physically moving a cable used to mean two separate actions in LinkLedger: disconnect the old connection, then make the new one. As of this version, the Connect port and + New cable pickers show an already-in-use port as selectable instead of graying it out — its label says exactly what it's currently connected to, e.g. eth0 -- in use, connected to patch-panel.example.lan (port 1).

Click Connect with an occupied port picked on either end, and a warning pops up naming exactly what's about to be disconnected -- something like "This will disconnect the source port (currently connected to X) and replace it with this new connection. Continue?" Confirm it, and the old connection is removed and the new one created in a single action. Cancel it, and nothing changes.

This works identically whether one end, both ends, or neither end is currently in use, and applies to wireless/virtual links the same way it applies to cables -- it's the fastest way to record a cable you've physically unplugged from one port and plugged into another.

Patch panels

A Patch Panel device shows two columns per numbered port: the device side (rear) — what's physically plugged into the back, in a wall jack — and the switch side (front) — the patch cable running from the front to a switch. + Add N paired ports creates however many front/rear pairs you need in one go, already linked as pass-through.

Connecting an unused rear port works the same as any other port — click its link icon, choosing the actual device on the other end of that wall run.

Once both sides of a pair are connected, anything plugged into the switch side traces straight through to the real device on the wall side — a connection chain like → patch-panel.example.lan (port 1) → desktop-pc.example.lan shows the whole path, not just the panel.

AP Groups & Virtual Switches

Some connections don't have one fixed physical end: a laptop associates to whichever access point is best right now, and a container reaches the network through its host's internal bridge, not a cable of its own. AP Group and Virtual Switch are two roles for exactly this — devices with no physical ports of their own, defined instead by:

  • Uplinks — real ports elsewhere that this virtual switch rides on top of. Each keeps its own normal cable too.
  • Members — ports whose only connection is this virtual switch, added from the member port's own link icon by choosing "Wireless / virtual link" instead of a cable.

From a member's own page, the connection just shows the group, with a note when there's more than one possible physical path:

The same pattern models containers and VMs — a Virtual Switch stands in for a Docker bridge, a Proxmox vmbr, or similar:

Chaining works too A container's vNIC can itself be a Virtual Switch's uplink — e.g. a Docker bridge running inside a VM. LinkLedger will trace all the way through: container → the VM's bridge → the VM's vNIC → the host's own bridge → the host's physical NIC → a normal cable from there.

LAGs (bonded links)

When two or more of a device's own ports are bonded into one logical link — a NAS with two NICs trunked together, or a switch-to-switch link over two cables — + Add LAG on that device's page groups them. Each member keeps its own individual cable exactly as before; a LAG is a label on top, not a replacement, so the path finder still traces each member on its own.

PoE tracking

Mark a switch/router port as Supplies PoE from its edit dialog, and mark any device as Requires PoE from Add/Edit device. Wherever that device's connection shows up, you'll see a green "PoE OK" badge, or an amber warning if the port it's actually plugged into doesn't supply power — a quick way to catch something that got moved to the wrong port.

Path finder

Search for a source device/NIC and a destination device/NIC, and see the actual path between them — every hop, which port it enters and leaves on, and each segment's speed.

When the NIC you picked is wirelessly/virtually linked to an AP Group or Virtual Switch with more than one uplink, a Via AP (or Via uplink) dropdown appears next to that picker. Leave it on "Best route (auto)" for the shortest path, or pin it to a specific uplink to see the route as if that device were actually using it right now.

VLANs change which kind of path is searched for: same VLAN (or untagged) looks for the plain shortest cabled path; two different tagged VLANs requires the path to pass through a Router/Firewall, since a plain switch can't legitimately bridge that. "No path found" means no such route exists — not that something's broken.

Reports

A set of read-only checks for gaps in your documentation — nothing here changes data, and every item links straight to the device in question.

Checks include: devices missing a site, model, or role; site values in use that aren't in your managed Sites list; ports missing a speed; ports with no cable, pairing, or wireless/virtual link at all; AP Groups/Virtual Switches with no uplinks; devices with no ports yet; and devices requiring PoE that aren't actually getting it.

Filtering the browse grid

On Browse devices, the type dropdown above the grid filters down to one role — useful once you've got more than a couple dozen devices.

Printing a device page

Every device page has a Print button. It opens your browser's normal print dialog, but first strips out the search bar, tabs, and every button/ action icon, leaving just that device's name/role/model/site, its notes, and its full port table on a clean page.

Settings, accounts & backups

This tutorial focuses on the Browse/Device/Path finder/Reports screens shown above; the Settings page (top right, admin sees the most) has its own controls that aren't screenshotted here since they're mostly self-explanatory forms:

  • Change your password — do this first on any real installation; see the callout in "Signing in" above.
  • Sites and Device roles / Interface speeds — manage the option lists the Add/Edit forms offer. All three start minimal/empty and are non-destructive: hiding or renaming an option never touches a device/port that's already using it.
  • Viewer account password — LinkLedger's read-only account gets a random password on first install that the admin never sees or needs. If you want to actually use that account, set a password for it here — no need to know the old one.
  • Backup (both accounts) and Restore (admin only) — the sample data linked at the top of this page is a real backup .zip, produced exactly this way, so it's a good first thing to try restoring.
  • Clear all connections and Reset data (admin only) — see "Clearing connections, or clearing everything" below.

The Help page covers all of these in full reference detail, including the exact CSV columns LinkLedger's backup/ restore format uses.

Clearing connections, or clearing everything

Settings has two increasingly destructive "start over" buttons, next to each other near the bottom of the page:

Clear all connections permanently disconnects every cable and wireless/virtual link, leaving your devices and ports themselves exactly as they are. Patch-panel front/rear pairing and LAG groupings aren't affected, since those describe what a port structurally is rather than what it's currently plugged into. This is the quicker option when you're physically re-cabling a large part of your network and would rather start the connections from a clean slate than disconnect each one individually -- a single confirmation dialog spells out what's about to happen before it runs.

Reset data goes further: it permanently deletes every device, port, and cable, and also clears your Sites list and resets Device roles / Interface speeds back to their full default (everything enabled) -- a genuinely blank slate to start documenting a different environment from scratch, including its own picker-setting customizations, not just its topology. It asks you to type "RESET" to confirm, since (like Clear all connections) it can't be undone -- download a backup first if there's any chance you'll want any of it back.

Edge cases worth knowing about

  • A device with an old/hidden role, site, or speed keeps its existing value even after that option is hidden from new-pick dropdowns in Settings — hiding only affects what's offered going forward, never existing data. Reports' "site values not in your managed list" check is a quick way to find these.
  • The Internet device is a documentation-only stand-in for "the public internet" — give it one port per site/ISP handoff. It doesn't bridge its own ports, so Path Finder won't route "through" it from one site's WAN port to another's; there isn't really one deterministic path through an ISP. A real site-to-site VPN tunnel is different — model it as an ordinary port-to-port cable between the two routers instead, and it's automatically traversable.
  • A device with only one port skips the "which NIC do you mean" step in Path Finder automatically; a multi-port device (like the NAS above) needs the specific NIC picked, since it can genuinely reach the same destination two different physical ways.
  • Restoring a partial backup only replaces what's actually in the .zip — a file with just ports.csv leaves devices, cables, and everything else untouched. See the Help page for exactly what cascades (e.g. replacing devices clears their ports and cables, since they can't exist without the device).
  • Every login re-checks the default-password reminder — if you dismissed it with "Remind me later" it'll simply reappear next time you sign in as admin, until the password is actually changed.
